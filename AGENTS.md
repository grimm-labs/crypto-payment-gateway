# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is

A Rust service that accepts **USDT deposits** on **Tron (TRC-20)**, **Ethereum (ERC-20)**, and **Solana (SPL)**, plus **BTC** on **Bitcoin** (on-chain, BIP84) and **Lightning** (BOLT11 invoices via the Breez SDK Spark). It derives a unique deposit address per payment from a single custodial HD wallet (`WALLET_MNEMONIC`) — or, for Lightning, issues an invoice — polls the blockchains for incoming transfers, confirms deposits, and sends payment-lifecycle webhooks — `PENDING` (address created), `PAID` (deposit confirmed), `EXPIRED` — to every active endpoint **subscribed to that event** (managed in the dashboard, stored in `webhook_endpoints` with an `events` array — no env var). Storage is PostgreSQL (sqlx); Redis backs the webhook queue, cached wallet balances, and staff refresh tokens.

An **admin dashboard** lives in `apps/dashboard` (Vite + React 19 + TypeScript + Tailwind v4 + shadcn/ui): wallet balances, payment/webhook monitoring and retry, API key and staff management. It talks exclusively to `/api/admin/v1` with the acting staff member's JWT (`Authorization: Bearer`). Merchant endpoints under `/api/v1` require an `x-api-key` created from the dashboard.

Scope today: **inbound deposit detection + webhooks + admin dashboard**, plus one outbound path: **Lightning-address payouts** from the Breez wallet (`POST /lightning/payments`, ADMIN staff or a merchant key granted `api_keys.canSend`). No other outbound transfers (no on-chain sends, no USDT), no multi-tenancy. Webhook endpoints are stored in DB (multiple, each active/inactive with per-event subscriptions) and managed from Dashboard → Webhooks (admin); the default payment expiry lives in `app_settings`, managed from Dashboard → Settings.

## Architecture

**Nx monorepo** (Nx 23, pnpm 11, Node 24 — `.tool-versions`) with two apps: `apps/api` (the Rust gateway binary, Cargo package `gateway`) and `apps/dashboard` (the SPA). Each Nx project is declared in the `nx` field of its `package.json`; there is no Nx plugin for Rust — the api's targets run cargo through `nx:run-commands`, and `packages/rust` is one Nx project (`rust`, an implicit dependency of `api`) so a Rust change affects `api` and a dashboard change affects only `dashboard`.

The Rust side is one Cargo workspace rooted at the repo root (version, edition, and all dependency versions are set in the root `Cargo.toml` via `[workspace.package]` / `[workspace.dependencies]` — never pin versions in a member crate): the binary in `apps/api`, the library crates in `packages/rust/<crate>`:

| Crate | Role |
|---|---|
| `config` | `AppConfig::from_env()` (→ `from_lookup`), shared constants (USDT contracts, `WEBHOOK_MAX_ATTEMPTS = 5`), RPC/Esplora URL builders, Redis key prefixing |
| `domain` | Pure types: `Network`, `Token`, statuses, `StaffRole`, `DomainError`, amount conversion/tolerance helpers. No I/O, no async |
| `wallet` | HD derivation from BIP39 mnemonic (own BIP32 on `k256`, private `bip32.rs`, checked against the official BIP32 vectors; the seed is held zeroize-on-drop). ETH/Tron via BIP44 `m/44'/60'/0'/0/{index}` (secp256k1); Bitcoin via BIP84 `m/84'/0'/0'/0/{index}` (P2WPKH `bc1q…`); Solana via SLIP-0010 `m/44'/501'/{index}'/0'` (ed25519), returning the USDT **associated token account** address. Lightning has no derived address (error) |
| `auth` | Pure auth primitives (no I/O, no async): argon2id password hashing (+ dummy-hash verification for unknown accounts), HS256 JWT issue/decode (`iss`/`aud`/`jti`/`sid` checked), refresh-token, session-id and API-key generation + SHA-256 hashing, constant-time comparison, webhook signatures (legacy body-only + timestamped V2) |
| `db` | `Db` wrapper over a `PgPool`, row structs, all SQL queries, sqlx migrations (`packages/rust/db/migrations/`). Split into `lib.rs` (payments/webhooks) + `staff.rs`, `api_keys.rs`, `admin_queries.rs`, `settings.rs`, `webhook_endpoints.rs`, `api_traffic.rs` (request log + aggregates), `payouts.rs` (`payout_requests`: idempotency + limits), `audit.rs` (append-only `audit_log`) |
| `chain` | HTTP clients for TronGrid, Alchemy (Ethereum JSON-RPC), Helius (Solana), Esplora (Bitcoin, `esplora.rs`): transfer polling + balance fetches, Tron rate-limit backoff, `confirmations_between` (saturating), boot-time mainnet identity checks (`verify_networks`, `mainnet.rs`). Every HTTP call goes through `request.rs` (errors stripped of their URL — provider keys live in URLs); raw reqwest calls are a compile error there (`clippy.toml` + `deny(disallowed_methods)`) |
| `lightning` | **Package `lightning-client`** (dir `packages/rust/lightning`) (`lightning` clashes with LDK's crate in the graph — use `-p lightning-client`). Thin Breez SDK Spark wrapper: SDK calls go through the `LightningOps` trait (mocked with mockall in tests), `LightningClient` maps requests and filters received Lightning payments. `jobs`/`http-api` never touch SDK types |
| `jobs` | `AppState` (shared by API + workers; `lightning: Option<LightningClient>`, `None` = disabled; `webhooks: WebhookClient`; `setup_token`), background workers (`spawn_workers`): one monitor loop per network, enabled or not (Lightning's reconciles from the Breez payment list), the Lightning event loop, webhook delivery loop, hourly wallet-balance sync, API traffic writer + retention purge (`traffic.rs`, `TrafficRecorder`); deposit confirmation logic (`process_detected_transfer`); manual retriggers (`retrigger_webhook`, `retrigger_failed_deposit_webhooks`, `retrigger_failed_webhooks`); payouts (`payouts.rs`: `request_payout`, `quote_payout`); audit trail (`audit.rs`); SSRF-hardened webhook client (`webhook_client.rs`) |
| `http-api` | Axum router (`http` was taken by the external crate): `/healthz`, `/readyz`, `/api/v1/*` (guarded by `x-api-key`), `/api/admin/v1/*` (guarded by staff JWT; admin-only sub-routes); `middleware.rs` (guards + `ClientIp` extractor) + `session.rs` (cookie sessions) + `rate_limit.rs` (Redis fixed windows) + `traffic.rs` (request-log middleware, client-IP resolution) + `admin.rs` (dashboard handlers, step-up TOTP); `ApiError` (`{"statusCode": ..., "message": ...}`) |
| `gateway` (`apps/api`) | The binary. Wires config → wallet → db (+ migrations) → redis → chain → workers → HTTP server |

Auth model: staff accounts live in `staff_users` (roles `ADMIN` / `OPERATOR`, argon2id hashes, `firstName`/`lastName`); merchant keys in `api_keys` (clear `prefix` for lookup + SHA-256 `keyHash`, revocation via `revokedAt`). Staff sessions (`session.rs`): a login opens `auth:session:{sid}` (absolute lifetime `REFRESH_TOKEN_TTL_DAYS` from the login, never extended), indexed in `auth:staff-sessions:{staff_id}`; its current refresh token `auth:refresh:{sha256}` → sid is consumed atomically on every refresh (Lua GET+DEL — no GETDEL, Redis < 6.2 must keep working) and replaced; rotated hashes are remembered (`auth:refresh:rotated:{sha256}`) and replaying one after a 30 s grace revokes the session. The refresh token travels only in the HttpOnly `cpg_refresh` cookie (`Path=/api/admin/v1/auth`, `SameSite=Strict`, `Secure` outside development); cookie routes (`/auth/refresh`, `/auth/logout`, both public) require the `X-CSRF-Protection` header. Access JWTs carry the `sid` and `require_jwt` checks the session exists, so revoking a session kills its access tokens immediately. The first admin is created through the dashboard's `/setup` wizard, which needs the one-time setup token (`SETUP_TOKEN`, or a random one printed at boot while `staff_users` is empty) and inserts under an advisory lock; there is no env-var seeding. `JWT_SECRET` (≥ 32 chars, shorter fails startup) is required or `/api/admin/v1` is not mounted. Sensitive admin actions need a fresh TOTP code (`admin::require_step_up`: payouts, `can_send` grants, payout limits, staff create/role/activation/password, 2FA reset); TOTP and current-password failures are budgeted per account (`rate_limit.rs`).

Dependency direction: `domain` ← everything; `http-api` and `jobs` sit on top; only `gateway` produces a binary. Put logic in the right layer — e.g. queue/DB logic belongs in `jobs`/`db`, not in API handlers.

Nx loads the root `.env` into every task (on top of the gateway's own dotenvy loading): a variable left **empty** in your shell is filled from `.env` — unset it or give it a value to override it for an `nx run`.

Migrations run automatically at boot via `sqlx::migrate!` (failure is logged as a warning, not fatal — so a migration must never fail on existing data: guard unique indexes over old rows with a `DO $$` duplicate check, see `20261012000000_security_hardening.sql`). There are **no DB integration tests** — unit tests live in `domain`, `wallet` (BIP39/BIP84/HD golden vectors), `config` (via `AppConfig::from_lookup`, never the process env), `chain` (Esplora parsing, confirmation math), `lightning-client` (mocked `LightningOps`), `auth`, `jobs` (traffic queue, Lightning matching, token totals) and `http-api` (request validation, traffic middleware via `tower::ServiceExt::oneshot`). If you change derivation logic, the golden-vector tests in `packages/rust/wallet/src/lib.rs` must still pass byte-for-byte.

## Conventions

- **DB naming is Prisma-style**: tables snake_case, columns **camelCase** and quoted (`"derivationIndex"`, `"expiresAt"`), Postgres enums PascalCase (`"Network"`). Rust row structs map them with `#[sqlx(rename = "...")]`. New SQL must follow this style, and enum values must be cast (`$1::"Network"`).
- **Three casings for enums** — keep them straight: DB values are UPPERCASE (`TRON`, `PENDING`), API strings are lowercase (`tron`, `pending`). Always convert through the `as_db` / `as_api` / `from_db` / `parse_api` methods in `domain`; never hand-write status strings.
- **Amounts**: `amount_raw` is the integer string in token base units (`Token::decimals()`: USDT 6, BTC 8 = sats); `amount` is a `Decimal` in `DECIMAL(24,8)` columns. Convert with `domain::raw_to_decimal*(raw, token)` / `decimal_to_raw` — never through floats — passing the token of the row. Deposit amounts in webhook payloads and the deposit-address detail go through `format_amount` (token-scale rendering, keeps USDT's historical `25.000000` now that columns are `DECIMAL(24,8)`). Matching against `expected_amount` uses `is_amount_within_tolerance` (`AMOUNT_TOLERANCE_PERCENT`, default 1%). Totals are per token: sats never enter `total_usdt` / `confirmed_volume` (USDT-only), BTC goes to `total_btc`.
- **Network ↔ token**: each network receives one token (`Network::token()`, `domain::supports`). BTC networks take `expected_amount_sats` (integer string) and reject `expected_amount`; USDT networks the reverse.
- **Redis keys** are always built via `config.redis_key(suffix)` → `stablecoin-payment-service-{APP_ENV}:{suffix}`. Never hardcode a full key. The namespace (`config::REDIS_NAMESPACE`) is the project's **former** name, frozen through the rename to *crypto-payment-gateway*: changing it orphans the webhook queue, staff sessions, the payout watermark and the balance cache (a test pins it).
- **Config**: all tuning goes through env vars read in `packages/rust/config/src/lib.rs` (with defaults) and documented in the README table. Missing provider API keys must *disable* the corresponding network with a startup warning, not crash — likewise an unset `BITCOIN_ESPLORA_BASE_URL` disables Bitcoin and an unset `BREEZ_API_KEY` (or a failed SDK connect) disables Lightning. But a value that is *set* and invalid or unsafe fails startup (`AppConfig::validate`): unparsable numbers, confirmation floors (ETH ≥ 12, Tron ≥ 19, BTC ≥ 1), tolerance 0–5 %, TTL bounds, short `JWT_SECRET`, `*` CORS origins, and — outside `APP_ENV=development` — the public test mnemonics, `http://` provider URLs, and Redis/Postgres without verified TLS (`rediss://`, `sslmode=verify-full`) unless `ALLOW_INSECURE_TRANSPORT=true`. A provider that answers for another chain at boot (`chain.verify_networks`) disables its network; a transient check failure only warns.
- Errors: `anyhow` at boundaries, `thiserror` enums inside `domain`/`wallet`. API errors go through `ApiError` so the JSON shape stays `{"statusCode", "message"}`; `ApiError::internal` (and every `From<anyhow/Redis/serde_json>`) logs the detail and answers a generic `"Internal server error"` — never put driver errors, constraint names or URLs in a response.
- **Audit**: every security-relevant mutation (staff, API keys, settings, webhook endpoints, sessions, 2FA, payouts, webhook replays) calls `jobs::audit::record` with the acting `Actor` (staff / API key + client IP). `details` never carries a secret. `audit_log` is append-only (DB trigger).
- Logging via `tracing`. **Never log the mnemonic or provider API keys.**

## Domain gotchas (easy to get wrong)

- **ID confusion in webhooks**: the webhook JSON field `data.deposit_id` is actually `deposit_addresses.id` (for every deposit/address event type; payout events carry `data.payment_id`, the SDK payment id, instead), while the Redis queue and `webhook_deliveries.depositId` hold `deposits.id` for PAID. This is intentional and load-bearing for existing receivers — do not "fix" the payload.
- **Expiry runs after a poll, per network**: each monitor loop polls its PENDING addresses (deadline passed or not — `pending_addresses` has no deadline filter) and only then calls `expire_addresses_and_notify(network, polled)`. An address expires once its deadline is `ADDRESS_EXPIRY_GRACE_SECS` (10 min) old **and** its last poll succeeded **and** it has no DETECTED deposit — or unconditionally `DETECTED_DEPOSIT_HOLD_SECS` (24 h) after the deadline. A disabled network only gets the 24 h hard stop. Nothing else expires payments (not the list endpoint, not boot), which is why there is no boot-time reconciliation any more: the first pass of every loop polls before it expires.
- **Event subscriptions**: `webhook_endpoints.events` (TEXT[], DB values `PENDING`/`PAID`/`EXPIRED`/`PAYOUT_SUCCEEDED`/`PAYOUT_FAILED`) gates every fan-out AND every delivery attempt (`deliver_webhook` re-checks it, like `isActive`). Payload `event_type` values are `payment_pending`, `deposit_confirmed` (historical name — never rename), `payment_expired`. PENDING fires on address creation (API handler), EXPIRED from `expire_addresses_and_notify` (called by monitor loops and the list endpoint), PAID at deposit confirmation. Payout events (`payout_succeeded`/`payout_failed`) fire for **every** finished send of the Lightning wallet — whoever sent it, the wallet may be shared — from the SDK event stream plus a boot catch-up (`catch_up_payouts`, Redis watermark `lightning:payout-watermark`, first boot only sets it).
- **Per-endpoint deliveries**: PAID deliveries are tracked per (deposit, endpoint) pair; PENDING/EXPIRED per (address, event, endpoint) with `depositId` NULL; payouts per (`lightningPaymentId`, event, endpoint) with `depositAddressId` NULL (a CHECK keeps exactly one subject). The authoritative row is the newest per key (`DISTINCT ON ("depositAddressId", "lightningPaymentId", "eventType", "depositId", "webhookEndpointId")` — keep `lightningPaymentId` in every such key). Rows with a NULL `webhookEndpointId` are pre-multi-endpoint history. Redis ZSET members are `"{deposit_id}|{endpoint_id}"` for PAID and `"{EVENT}|{subject_id}|{endpoint_id}"` for address and payout events (subject = address id / SDK payment id, both UUIDs); a bare member (no `|`) is legacy and gets fanned out to all active PAID endpoints by `webhook_loop`. No active endpoints = webhooks silently disabled (503 only on manual retry).
- **Admin-managed settings**: default payment expiry is `app_settings.depositExpiryMinutes` (default 60, max 1440), not an env var. Likewise the traffic-log retention is `app_settings.apiTrafficRetentionDays` (default 730; `0` = keep forever, surfaced as `null` in the API), re-read by the purge loop on every hourly tick.
- **API traffic log** (`api_requests`, Dashboard → Traffic): the `record_traffic` middleware must stay *outside* the auth guards in `router()` (added after both `nest`s, via `.layer` not `.route_layer`) so it sees rejected requests and the identity the guards copy into the **response** extensions (`CurrentApiKey` / `CurrentStaff`). It stores the matched route template, never the raw path or bodies, and **never the raw `x-api-key`** — only `apiKeyId`. The client IP honours forwarding headers only when the TCP peer is in `TRUSTED_PROXIES` (then the **last** `X-Forwarded-For` hop); otherwise it is the socket address. Recording is a non-blocking `try_send` into a bounded channel; drops are counted and exposed as `dropped_events`. `/api/v1` is the `MERCHANT` surface, `/api/admin/v1` is `ADMIN` (the dashboard's own polling — hidden by default in the UI); health checks are not recorded.
- **API key format**: `[{tag}_]{8 alnum}_{40 alnum}`. The tag is `app_settings.apiKeyPrefix` (≤ 5 alphanumeric chars, empty = no tag) and only affects newly generated keys. `auth::parse_api_key_prefix` is deliberately tag-agnostic (splits on the last `_`) so keys issued under any past tag — including the historic `spg` — keep validating after the setting changes. Never re-tighten it to a specific tag.
- **API key expiry**: `api_keys.expiresAt` (NULL = never) with status machine `ACTIVE`/`REVOKED`/`EXPIRED`. Enforcement is two-level: `find_api_key_by_prefix` rejects past-deadline keys immediately (the security boundary), while `api_key_expiry_loop` (5 min, first run at boot) only materializes `EXPIRED` for listings/stats. List handlers derive the displayed status so a key can never show `active` after its deadline, even between sweeps.
- **Confirmation thresholds**: Tron 19, Ethereum 12, Bitcoin 3 (env-overridable with floors, see Config), Solana hardcoded to 1 (`finalized` commitment, failed transactions skipped), Lightning 1 (a settled payment is final) — `domain::required_confirmations`. Tron reads only solidified history (`only_confirmed=true`) and resolves each transfer's real block through `walletsolidity/gettransactioninfobyid` (TronGrid's trc20 listing has no block number; never invent one). Provider responses are re-checked for the USDT contract. Zero-amount transfers never settle anything; `expected_amount` must be > 0.
- **Lightning rows**: `deposit_addresses.address` holds the BOLT11 payment request (matched by exact string) and `deposits.txHash` holds the SDK `Payment.id` — no dedicated payment-hash column. Two detection paths (SDK `PaymentSucceeded` events + a reconciliation poll from the oldest pending invoice) both converge on `process_detected_transfer`, made idempotent by the (address, txHash) upsert. The Lightning monitor loop reconciles every PENDING invoice (deadline passed or not) before its expiry sweep, so invoices paid during downtime are credited, not expired. SDK error strings are logged, never returned to clients (a failed payout answers a generic `502 "Payment failed"`). `GET /lightning/payments` (`canSend` keys + ADMIN staff) pages the *whole* wallet history (`has_more`, no total), linking entries to gateway invoices via `deposit_address_id`. Merchant webhooks stay on the gateway's own queue — SDK events only feed detection (received payments) and payout notification (finished sends). Payouts accept `user@domain` only (no IP literals / local TLDs, and outside development the domain must resolve to public addresses: the SDK fetches it), and a replayed `Idempotency-Key` is answered from storage (`get_payment(key)`, which must be a *send*) before the address is resolved again. `POST /lightning/payments/quote` prepares without paying (fee preview).
- **Webhook delivery**: max 5 attempts (`WEBHOOK_MAX_ATTEMPTS`), 1 s loop, up to `WEBHOOK_DELIVERY_CONCURRENCY` (16) concurrent deliveries, 10 s HTTP timeout, only the *last* response/error is stored (`err.without_url()` — never the endpoint URL). Members are *claimed* atomically (Lua) from the queue ZSET into `zset:webhook-inflight` (score = lease expiry, `WEBHOOK_CLAIM_LEASE_SECS`): a member is never delivered twice concurrently (overlapping containers included), and a worker dying mid-delivery leaves a lease that puts the member back in the queue (at-least-once). Releasing reschedules with "keep the earlier score" semantics. Undecodable members (anything containing `|` that does not decode) are dropped, never re-fanned. A delivery whose endpoint went inactive/unsubscribed or whose subject is gone closes its PENDING row as FAILED instead of leaving it pending. Delivery rows are unique per key (partial unique indexes; `get_or_create_*` use `ON CONFLICT DO NOTHING` + re-select). Payloads carry top-level `event_id` (= delivery id = `X-Webhook-Id`) and `occurred_at`.
- **Webhook client** (`jobs::webhook_client`, `AppState.webhooks`): outside development `https://` only, no credentials in the URL, no internal names or non-public IP literals, a DNS resolver that only returns public addresses (`domain::is_public_ip`), and **no redirects** (3xx = failed attempt). In development `http://` and private receivers are allowed. Endpoint creation runs the same checks plus a DNS resolution.
- **Webhook signing**: `webhook_endpoints.secret` is stored in clear (HMAC needs it) but is **write-only through the API** — responses only carry `has_secret`; never serialize `WebhookEndpointRow.secret` into a handler response (its `Debug` is redacted). A secret is required at creation and cannot be removed (legacy unsigned endpoints keep delivering unsigned until one is set). Every delivery carries `X-Webhook-Id`, `X-Webhook-Timestamp`, `X-Webhook-Signature` (`sha256=<hex>` of the body, `auth::webhook_signature`) and `X-Webhook-Signature-V2` (`t=<ts>,v1=<hex>` of `"<ts>.<body>"`, `auth::webhook_signature_v2`), all computed over the exact body bytes sent — the payload is serialized once with `serde_json::to_vec` and that same buffer is signed and sent; never re-serialize separately.
- **Payouts** (`jobs::payouts`): the `Idempotency-Key` (UUID, required — it is also the SDK payment id) is reserved in `payout_requests` with the caller (`apiKeyId` xor `staffId`) and a hash of the parameters, under an advisory lock that also checks the limits (`app_settings.payoutMaxSats` / `payoutDailyMaxSats`, rolling 24 h over PENDING+SENT requests; `0` disables payouts). Same key + caller + parameters already SENT → the stored payment (200), nothing re-sent; other caller/parameters → 422; PENDING younger than `PAYOUT_STALE_PENDING_SECS` → 409; FAILED or stale PENDING → re-reserved (the SDK answers a sent key from its storage). The SDK call is bounded by `PAYOUT_TIMEOUT_SECS`. A key with `canSend` must expire (DB CHECK); granting it needs a TOTP step-up. The Lightning history is readable only by `canSend` keys and ADMIN staff.
- Two independent status machines: deposit (`DETECTED` → `CONFIRMED`) tracks on-chain state; webhook (`PENDING`/`DELIVERED`/`FAILED`) tracks HTTP notification state. Never let one mutate the other.
- A deposit is unique per `("depositAddressId", "txHash")` (one Bitcoin tx can pay several gateway addresses) — look deposits up by both; derivation indices are allocated atomically per network from `derivation_counters` (`next_derivation_index`, Lightning too, though no key depends on it); `(network, derivationIndex)` is unique.
- **Merchant API bounds**: `expires_at` within [now + 1 min, now + 1440 min]; at most `MAX_PENDING_ADDRESSES_PER_API_KEY` open payments per key (`deposit_addresses.apiKeyId`); a disabled network answers 503; `/balances` is served from a 5-minute Redis cache recomputed in the background (503 + `Retry-After` while computing); merchant webhook replays re-queue FAILED deliveries only; merchant responses never include endpoint URLs or delivery errors. Rate limits live in `http-api/src/rate_limit.rs` (Redis fixed windows keyed by the hashed identity).
- **Client IP** (`traffic::resolve_client_ip`, used by the traffic log, rate limits and audit): forwarding headers count only when the TCP peer is in `TRUSTED_PROXIES`; `X-Forwarded-For` is then walked from the right and the first untrusted hop is the client.
- Polling loops sleep `ADDRESS_REQUEST_DELAY_MS` (300ms) between addresses to respect provider rate limits; TronGrid additionally has an explicit backoff on 429s in `chain`.

## Security rules

This is a **custodial hot-wallet** service — treat everything key-related as sensitive:

- Never commit `.env`, real mnemonics, API keys, or production credentials. `.env.example` only uses the well-known BIP39 test vector (`abandon … about`) — refused outside development (`config::is_public_test_mnemonic`), and Lightning never connects with it.
- `AppConfig`, `WebhookEndpointRow` and `StaffUserRow` have hand-written, redacting `Debug` impls, and `AppConfig` zeroizes its secrets on drop: keep it that way when adding a secret field.
- Address derivation must remain deterministic — changing paths or hashing breaks recovery of funds on already-issued addresses.
- The Breez SDK is seeded with the same `WALLET_MNEMONIC` (Spark paths do not collide with BIP44/84). Lightning funds sit in the Spark L2 wallet, a different custody model (README → Custody note); its storage (`BREEZ_STORAGE_DIR`, absolute) must persist, and `gateway` disconnects the SDK on SIGINT/SIGTERM.

## Git / CI / releases

- CI (`.github/workflows/ci.yml`) runs on every push/PR: `pnpm nx affected -t lint test build` (Rust toolchain + `protoc` from the shared `setup-rust` action; cargo runs `--locked`, clippy `-D warnings` — refresh `Cargo.lock` after editing a `Cargo.toml`), `cargo deny check` (`deny.toml`; a new ignore needs a reason), then a build of the `all` Docker image on pushes. Third-party actions are pinned by full commit SHA and base images by digest (the Dockerfile hard-codes Node 24.21.0: keep it in sync with `.tool-versions`); Dependabot proposes updates.
- Docker: one multi-stage `docker/Dockerfile` (targets `api`, `dashboard`, `all`); the dashboard's nginx config lives in `docker/dashboard/` (non-root, port 8080, `/up` health check, `/api` proxied to `API_URL`). `compose.yaml` runs the whole stack from images, `compose.dev.yaml` only postgres + redis (same project name and volumes).
- Deploys: **Kamal** (`config/deploy.yml`, one file for test/staging/production; `.kamal/secrets` holds env-var references only). Deploy runs only from `main` / `v*` for a commit on `main` with a green CI (a `guard` job), verifies the server's host key (`vars.SSH_KNOWN_HOSTS`, `StrictHostKeyChecking yes`, `ssh.config: true`), and both roles run with `no-new-privileges` + `cap-drop ALL` (dashboard read-only). nginx (`docker/dashboard/`) verifies the API certificate and adds the security headers of `security-headers.conf` — any location that adds a header must include it again. One image (target `all`) runs as two roles — `api` (proxy `API_HOST`, port 3000, health `/readyz`, Breez volume via role `options.volume`) and `dashboard` (`/app/dashboard/start.sh`, proxy `DASHBOARD_HOST`, port 8080). Postgres and Redis are external. `.github/workflows/deploy.yml` (manual, per GitHub environment) runs `kamal deploy`; hosts come only from GitHub variables (`GATEWAY_HOST`, `API_HOST`, `DASHBOARD_HOST`). A deploy overlaps the old and new api containers for a few seconds on the Breez volume (accepted: idempotent processing). Never put a secret value in `config/deploy.yml` or `.kamal/secrets`.
- Releases are **manual** via the "New App Version" workflow (`workflow_dispatch`): it bumps the workspace version with `cargo set-version`, commits `chore: release vX.Y.Z`, tags, and publishes the Docker image. Never bump the version or create tags by hand.
- Do not commit or push unless the user asks. Keep PRs scoped to one concern; add tests when changing `domain` or `wallet` logic.
