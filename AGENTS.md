# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is

A Rust service that accepts **USDT deposits** on **Tron (TRC-20)**, **Ethereum (ERC-20)**, and **Solana (SPL)**, native **ETH** on Ethereum, plus **BTC** on **Bitcoin** (on-chain, BIP84) and **Lightning** (BOLT11 invoices via the Breez SDK Spark). It derives a unique deposit address per payment from a single custodial HD wallet (`WALLET_MNEMONIC`) — or, for Lightning, issues an invoice — polls the blockchains for incoming transfers, confirms deposits — a payment is the confirmed total of its transfers, watched 24 h past its deadline (ADR 0005) — and sends payment-lifecycle webhooks — `PENDING` (address created), `PAID` (the confirmed total reached the amount), `EXPIRED`, `LATE` (a late deposit confirmed) — plus withdrawal, payout and alert events to every active endpoint **subscribed to that event** (managed in the dashboard, stored in `webhook_endpoints` with an `events` array — no env var). Storage is PostgreSQL (sqlx); Redis backs the webhook queue, cached wallet balances, and staff refresh tokens.

An **admin dashboard** lives in `apps/dashboard` (Vite + React 19 + TypeScript + Tailwind v4 + shadcn/ui): projects and their balances, wallet balances, payment/webhook monitoring and retry, withdrawals and approvals, internal transfers, treasury/sweeps/ledger/address book/alerts, API key and staff management. It talks exclusively to `/api/admin/v1` with the acting staff member's JWT (`Authorization: Bearer`). Merchant endpoints under `/api/v1` require an `x-api-key` created from the dashboard.

Scope today: **inbound deposit detection + webhooks + admin dashboard**, plus **withdrawals** of every held asset (`docs/eth-and-withdrawals-spec.md`): USDT on Tron/Ethereum/Solana, ETH, BTC on-chain and over Lightning (Lightning address or BOLT11), and the TRX/SOL gas reserves (admin-only), from one **treasury** per network fed by **sweeps** of deposit addresses (Bitcoin is never swept: withdrawals spend deposit UTXOs). Callers: ADMIN staff (TOTP) or a merchant key with a withdrawal policy (`api_keys.withdrawalPolicy` `NONE`/`BOOK`/`OPEN`). `POST /lightning/payments` is a deprecated alias creating a Lightning withdrawal (`Deprecation` + `Sunset` headers). **Projects** (`docs/projects-spec.md`, `docs/adr/0004-projects-ledger-over-pooled-custody.md`, glossary in `CONTEXT.md`): one instance serves several applications of a single **merchant** (the operator); every key, deposit address, withdrawal, webhook endpoint and address-book entry has an **owner** (a project, or the **merchant funds** where allowed), the merchant API is scoped to the key's project, and a project balance is a *ledger over pooled custody* — derived from source rows, never stored, never a separate wallet. Projects are not tenants. No cold signer: everything is signed in-process. Webhook endpoints are stored in DB (multiple, each active/inactive with per-event subscriptions) and managed from Dashboard → Webhooks (admin); the default payment expiry lives in `app_settings`, managed from Dashboard → Settings.

## Architecture

**Nx monorepo** (Nx 23, pnpm 11, Node 24 — `.tool-versions`) with two apps: `apps/api` (the Rust gateway binary, Cargo package `gateway`) and `apps/dashboard` (the SPA). Each Nx project is declared in the `nx` field of its `package.json`; there is no Nx plugin for Rust — the api's targets run cargo through `nx:run-commands`, and `packages/rust` is one Nx project (`rust`, an implicit dependency of `api`) so a Rust change affects `api` and a dashboard change affects only `dashboard`.

The Rust side is one Cargo workspace rooted at the repo root (version, edition, and all dependency versions are set in the root `Cargo.toml` via `[workspace.package]` / `[workspace.dependencies]` — never pin versions in a member crate): the binary in `apps/api`, the library crates in `packages/rust/<crate>`:

Auth model: staff accounts live in `staff_users` (roles `ADMIN` / `OPERATOR`, argon2id hashes, `firstName`/`lastName`); merchant keys in `api_keys` (clear `prefix` for lookup + SHA-256 `keyHash`, revocation via `revokedAt`, `projectId` — carried as `CurrentApiKey.project_id`, `None` only for a legacy key before the first project exists). Staff sessions (`session.rs`): a login opens `auth:session:{sid}` (absolute lifetime `REFRESH_TOKEN_TTL_DAYS` from the login, never extended), indexed in `auth:staff-sessions:{staff_id}`; its current refresh token `auth:refresh:{sha256}` → sid is consumed atomically on every refresh (Lua GET+DEL — no GETDEL, Redis < 6.2 must keep working) and replaced; rotated hashes are remembered (`auth:refresh:rotated:{sha256}`) and replaying one after a 30 s grace revokes the session. The refresh token travels only in the HttpOnly `cpg_refresh` cookie (`Path=/api/admin/v1/auth`, `SameSite=Strict`, `Secure` outside development); cookie routes (`/auth/refresh`, `/auth/logout`, both public) require the `X-CSRF-Protection` header. Access JWTs carry the `sid` and `require_jwt` checks the session exists, so revoking a session kills its access tokens immediately. The first admin is created through the dashboard's `/setup` wizard, open to anyone while `staff_users` is empty (no setup token, by the operator's choice: they open it right after the first deploy), which inserts under an advisory lock; there is no env-var seeding. `JWT_SECRET` (≥ 32 chars, shorter fails startup) is required or `/api/admin/v1` is not mounted. Sensitive admin actions need a fresh TOTP code (`admin::require_step_up`: withdrawal create/approve/reject/cancel/bump/abandon, internal transfers, withdrawal grants, asset settings, address-book changes, sweeps run, lifting the freeze, staff create/role/activation/password, 2FA reset — project management needs none, only audit); TOTP and current-password failures are budgeted per account (`rate_limit.rs`).

Dependency direction: `domain` ← everything; `http-api` and `jobs` sit on top; only `gateway` produces a binary. Put logic in the right layer — e.g. queue/DB logic belongs in `jobs`/`db`, not in API handlers.

```bash
pnpm install                                  # Node 24 (asdf/.nvmrc), pnpm 11.25.0

# Run locally (needs .env — copy from .env.example; set JWT_SECRET for the admin API)

pnpm nx affected -t lint test build
pnpm nx run api:test                          # cargo test --workspace --locked (no DB, no network)
pnpm nx run api:lint                          # cargo clippy --workspace --all-targets --locked -- -D warnings

pnpm nx run-many -t build lint --projects=dashboard

# Full stack in Docker: postgres + redis + api (:3000) + dashboard (:8080)
docker compose up --build                     # compose.yaml, docker/Dockerfile targets api / dashboard
```

Nx loads the root `.env` into every task (on top of the gateway's own dotenvy loading): a variable left **empty** in your shell is filled from `.env` — unset it or give it a value to override it for an `nx run`.

Migrations run automatically at boot via `sqlx::migrate!` (failure is logged as a warning, not fatal — so a migration must never fail on existing data: guard unique indexes over old rows with a `DO $$` duplicate check, see `20261012000000_security_hardening.sql`). There are **no DB integration tests** — unit tests live in `domain` (incl. project validators, the webhook owner rule / legacy split, ledger arithmetic), `wallet` (BIP39/BIP84/HD golden vectors), `config` (via `AppConfig::from_lookup`, never the process env), `chain` (Esplora parsing, received-at-depth, confirmation math), `lightning-client` (mocked `LightningOps`), `auth`, `jobs` (traffic queue, Lightning matching, token totals, owner fan-out, transfer rules, shortfall counter) and `http-api` (request validation, traffic middleware and the router's surfaces via `tower::ServiceExt::oneshot` on `test_support`'s stub state). If you change derivation logic, the golden-vector tests in `packages/rust/wallet/src/lib.rs` must still pass byte-for-byte.

## Conventions

- **DB naming is Prisma-style**: tables snake_case, columns **camelCase** and quoted (`"derivationIndex"`, `"expiresAt"`), Postgres enums PascalCase (`"Network"`). Rust row structs map them with `#[sqlx(rename = "...")]`. New SQL must follow this style, and enum values must be cast (`$1::"Network"`).
- **Three casings for enums** — keep them straight: DB values are UPPERCASE (`TRON`, `PENDING`), API strings are lowercase (`tron`, `pending`). Always convert through the `as_db` / `as_api` / `from_db` / `parse_api` methods in `domain`; never hand-write status strings.
- **Amounts**: `amount_raw` is the integer string in token base units (`Token::decimals()`: USDT 6, BTC 8 = sats, ETH 18 = wei, TRX 6 = sun, SOL 9 = lamports); deposit `amount` is a `Decimal` in `DECIMAL(38,18)` columns. Convert with `domain::raw_to_decimal*(raw, token)` / `decimal_to_raw` — never through floats — passing the token of the row. Deposit amounts in webhook payloads and the deposit-address detail go through `format_amount` (token-scale rendering, keeps USDT's historical `25.000000`). Every withdrawal-side table (withdrawals, outbound transactions, sweeps, settings, limits) stores base units in `NUMERIC(78,0)`, read and bound as `db::RawAmount` (text cast ↔ `u128`) — never `Decimal`, never `f64`; Alchemy's float `value` is never read (use `rawContract.value`). A payment is the confirmed total of its deposits: `is_amount_paid(total_raw, expected_raw, AMOUNT_TOLERANCE_PERCENT)` (default 1 %, a lower bound only — an overpayment pays; integer arithmetic on base units, never floats). Totals are per token: sats never enter `total_usdt` / `confirmed_volume` (USDT-only); BTC goes to `total_btc`, ETH to `total_eth`, gas reserves to `total_trx` / `total_sol`. Balances are one entry per (network, token).
- **Network ↔ token**: payments: `Network::payment_tokens()` / `domain::supports` (USDT on tron/ethereum/solana, ETH on ethereum, BTC on bitcoin/lightning); withdrawals: `withdrawable_tokens()` / `domain::is_withdrawable` (adds the gas tokens TRX/SOL — `Token::is_gas_only`, admin-only, never a payment). BTC networks take `expected_amount_sats` (integer string) and reject `expected_amount`; USDT/ETH the reverse.
- **Redis keys** are always built via `config.redis_key(suffix)` → `stablecoin-payment-service-{APP_ENV}:{suffix}`. Never hardcode a full key. The namespace (`config::REDIS_NAMESPACE`) is the project's **former** name, frozen through the rename to *crypto-payment-gateway*: changing it orphans the webhook queue, staff sessions, the payout watermark and the balance cache (a test pins it).
- **Config**: `CHAIN_MODE=testnet` (Sepolia, Nile, devnet, testnet4, Spark regtest) is refused outside `APP_ENV=development` and requires the `TESTNET_USDT_*` contracts; boot checks the chain identity of each mode. All tuning goes through env vars read in `packages/rust/config/src/lib.rs` (with defaults) and documented in the README table. Missing provider API keys must *disable* the corresponding network with a startup warning, not crash — likewise an unset `BITCOIN_ESPLORA_BASE_URL` disables Bitcoin and an unset `BREEZ_API_KEY` (or a failed SDK connect) disables Lightning. But a value that is *set* and invalid or unsafe fails startup (`AppConfig::validate`): unparsable numbers, confirmation floors (ETH ≥ 12, Tron ≥ 19, BTC ≥ 1), tolerance 0–5 %, TTL bounds, short `JWT_SECRET`, `*` CORS origins, and — outside `APP_ENV=development` — the public test mnemonics, `http://` provider URLs, and Redis/Postgres without verified TLS (`rediss://`, `sslmode=verify-full`) unless `ALLOW_INSECURE_TRANSPORT=true`. A provider that answers for another chain at boot (`chain.verify_networks`) disables its network; a transient check failure only warns.
- Errors: `anyhow` at boundaries, `thiserror` enums inside `domain`/`wallet`. API errors go through `ApiError` so the JSON shape stays `{"statusCode", "message"}`; `ApiError::internal` (and every `From<anyhow/Redis/serde_json>`) logs the detail and answers a generic `"Internal server error"` — never put driver errors, constraint names or URLs in a response.
- **Audit**: every security-relevant mutation (staff, API keys, settings, webhook endpoints, sessions, 2FA, payouts, webhook replays, projects, internal transfers) calls `jobs::audit::record` with the acting `Actor` (staff / API key + client IP). `details` never carries a secret. `audit_log` is append-only (DB trigger).
- Logging via `tracing`. **Never log the mnemonic or provider API keys.**

## Domain gotchas (easy to get wrong)

- **ID confusion in webhooks**: the webhook JSON field `data.deposit_id` is actually `deposit_addresses.id` (for every deposit/address event type; payout events carry `data.payment_id`, the SDK payment id, instead), while the Redis queue and `webhook_deliveries.depositId` hold `deposits.id` for PAID and LATE. This is intentional and load-bearing for existing receivers — do not "fix" the payload.
- **A payment is the total of its transfers** (`docs/adr/0005-un-paiement-est-la-somme-de-ses-envois.md`): every non-zero transfer to a watched address is a deposit, `DETECTED` then `CONFIRMED`, whatever its amount (no per-transfer tolerance any more). `Db::upsert_deposit_and_maybe_pay` locks the address row (`FOR UPDATE`, address before deposit — keep that order), upserts the deposit, and when the call confirms one of a `PENDING` address computes `SUM("amountRaw"::numeric)` of its CONFIRMED deposits and sets `PAID` with an update that re-checks `PENDING`: it returns whether this call paid it, and `paid` fans out only then (once per payment, keyed on the deposit that tipped the total). **Late watch**: `deposit_addresses."watchUntil"` = `expiresAt` + `LATE_WATCH_HOURS` (24, 0–72, 0 = off); `Db::watched_addresses` (the SQL of `domain::is_watched`) = the PENDING addresses plus the PAID / EXPIRED ones whose watch is open or that hold a DETECTED deposit, never Lightning once it left PENDING. A transfer first seen once the address left PENDING is a **late deposit** (`deposits.late`, decided under the lock by `domain::admit_transfer`; a new transfer after the watch, or to a Lightning invoice no longer pending, is not recorded): followed to its confirmations, counted in the confirmed total and the ledger, swept like any other, **never changes the address's status**, and fires `LATE` (`deposit_late`, subject `Deposit`) once confirmed. A gateway outbound transaction (gas top-up) seen on a deposit address is never a deposit (`is_gateway_outbound_tx`). The deposit-address responses (create, list, GET) carry `received_amount(_raw)` (confirmed total, late included), `required_confirmations`, `watch_until`, `token_account`; `deposits[].late` in the GET. Payloads: `paid` and `late` add `expected_amount_raw` / `received_amount_raw` (`late` also `address_status`), `expired` adds `received_amount_raw`. Admin replays of a deposit send `late` for a late deposit and `paid` only for a deposit of a PAID address (`RetriggerError::NoDepositEvent` otherwise).
- **Expiry runs after a poll, per network**: each monitor loop polls its watched addresses (PENDING first, deadline passed or not — `watched_addresses` has no deadline filter on PENDING) and only then calls `expire_addresses_and_notify(network, polled)`. An address expires once its deadline is `ADDRESS_EXPIRY_GRACE_SECS` (10 min) old **and** its last poll succeeded **and** it has no DETECTED deposit — or unconditionally `DETECTED_DEPOSIT_HOLD_SECS` (24 h) after the deadline. A disabled network only gets the 24 h hard stop. Nothing else expires payments (not the list endpoint, not boot), which is why there is no boot-time reconciliation any more: the first pass of every loop polls before it expires.
- **Event subscriptions**: `webhook_endpoints.events` (TEXT[], DB values `PENDING`/`PAID`/`EXPIRED`/`LATE`/`PAYOUT_SUCCEEDED`/`PAYOUT_FAILED`, the withdrawal events `WITHDRAWAL_PENDING_APPROVAL`/`_BROADCAST`/`_CONFIRMED`/`_FAILED`/`_CANCELLED`, `TRANSFER_COMPLETED`, and the alert events `GAS_RESERVE_LOW`/`TREASURY_CAP_EXCEEDED`/`ADDRESS_BOOK_ENTRY_ADDED`/`WITHDRAWAL_STUCK`/`LEDGER_SHORTFALL`) gates every fan-out AND every delivery attempt (`deliver_webhook` re-checks it, like `isActive`). **Events follow their owner** (`WebhookEventType::owner_rule`): payment events go to the endpoints of the address's project, withdrawal events to those of the withdrawal's owner (project, or merchant endpoints for merchant funds), `TRANSFER_COMPLETED` to both sides' endpoints (union, deduplicated), alerts and `PAYOUT_*` to merchant endpoints only — enforced by `db::active_webhook_endpoints_for_event(event, owner)` on **every** fan-out path (PAID, `notify_address_event`, `notify_withdrawal`, `notify_payout`, `alerts::raise`, transfers, every `retrigger_*`, the legacy bare-member fan-out) through `jobs::webhooks`, and re-checked before every attempt (`check_endpoint`: a delivery whose endpoint belongs to another owner is closed FAILED). An endpoint may only subscribe to the events of its owner kind (`domain::allowed_events`: project = payments + withdrawals + transfer; merchant = withdrawals + transfer + payouts + alerts; else 422). Payload `event_type` values are `payment_pending`, `deposit_confirmed` (historical name — never rename), `payment_expired`, `deposit_late`; the other events use their API name (`withdrawal_confirmed`, `gas_reserve_low`, `transfer_completed`, `ledger_shortfall`, …); payment and withdrawal payloads carry `data.project_id` (additive; `null` for merchant funds). Sweeps and gas top-ups are never notified. PENDING fires on address creation (API handler), EXPIRED from `expire_addresses_and_notify` (called by the monitor loops), PAID when a confirmation makes the confirmed total pay the address, LATE when a late deposit is confirmed. Payout events (`payout_succeeded`/`payout_failed`) fire for every finished send of the Lightning wallet **the gateway did not make** (`db.is_gateway_send`: gateway withdrawals fire `withdrawal_*` instead; the wallet may be shared) — from the SDK event stream plus a boot catch-up (`catch_up_payouts`, Redis watermark `lightning:payout-watermark`, first boot only sets it).
- **Per-endpoint deliveries**: PAID and LATE deliveries are tracked per (deposit, event, endpoint) (`webhook_deliveries_deposit_event_key`; `*_deposit_webhook_delivery(event, …)`); PENDING/EXPIRED per (address, event, endpoint) with `depositId` NULL; payouts per (`lightningPaymentId`, event, endpoint), withdrawal events per (`withdrawalId`, event, endpoint), alert events per (`alertId`, event, endpoint), transfers per (`transferId`, event, endpoint) — a CHECK (`num_nonnulls`) keeps exactly one of `depositAddressId` / `lightningPaymentId` / `withdrawalId` / `alertId` / `transferId`, and `WebhookEventType::subject()` says which. The authoritative row is the newest per key (`DISTINCT ON ("depositAddressId", "lightningPaymentId", "withdrawalId", "alertId", "transferId", "eventType", "depositId", "webhookEndpointId")` — keep every subject column in every such key, `transferId` included). Rows with a NULL `webhookEndpointId` are pre-multi-endpoint history. Redis ZSET members are `"{deposit_id}|{endpoint_id}"` for PAID and `"{EVENT}|{subject_id}|{endpoint_id}"` for every other event (LATE: `"LATE|{deposit_id}|{endpoint_id}"`) (subject = address id / SDK payment id / withdrawal id / alert id / transfer id, all UUIDs); a bare member (no `|`) is legacy and gets fanned out to all active PAID endpoints by `webhook_loop`. No active endpoints = webhooks silently disabled (503 only on manual retry).
- **Admin-managed settings**: default payment expiry is `app_settings.depositExpiryMinutes` (default 60, max 1440), not an env var. Withdrawal guard rails live in `asset_settings` (per token: per-withdrawal / rolling-24 h limits, approval threshold, hot-wallet cap, gas floor and alert threshold — base units, `0` disables, a missing row means disabled), `sweep_settings` (per network+token minimum and switch) and `api_key_withdrawal_limits` (per key and token). The outflow freeze is `app_settings.outflowsFrozen` OR `OUTFLOWS_FROZEN`, read fail-closed (an unreadable setting counts as frozen). Likewise the traffic-log retention is `app_settings.apiTrafficRetentionDays` (default 730; `0` = keep forever, surfaced as `null` in the API), re-read by the purge loop on every hourly tick.
- **Projects — ownership model** (spec §5): a key and a deposit address belong to a project (required; the address inherits the key's or takes the staff member's `project_id`); a key's withdrawal to the key's project; an admin withdrawal, a webhook endpoint and an address-book entry to a project **or the merchant** (`project_id: "merchant"`, chosen explicitly — no default); an internal transfer has two owner sides; alerts and non-gateway Lightning sends are the merchant's. Treasuries, sweeps, gas, the freeze, asset/sweep settings, alerts as objects, staff, audit and app settings have no owner. TRX/SOL withdrawals are merchant-only (DB CHECK on `withdrawals`). Owners are set at creation and never change (`PATCH /webhook-endpoints` refuses `project_id`). Project CRUD is admin, no TOTP, audited; a project is deleted only when nothing references it and never when it is the last one.
- **Projects — invariants** (spec §4, each covered by a test or a structural guarantee): (1) one owner forever; once a project exists no active key lacks one. (2) The merchant surface is scoped **in SQL**: every `/api/v1` read and mutation goes through `OwnerFilter` / `owner_condition`, `find_deposit_address_owned`, `find_deposit_owned`, `find_withdrawal_visible`, `find_internal_transfer_for_project` — another project's object answers `404` exactly like a missing one, never `403`, and no bare `WHERE id = $1` on the merchant surface (`http_api::merchant_scope`). (3) A key withdrawal fits in its project's `available` (amount + fee cap when `token == fee_token`), checked inside the per-asset advisory-lock admission transaction and again at approval (`project_insufficient_funds`); transfers take the same lock. (4) Balances are derived on every read from deposits, sweeps, `btcReceivedRaw`, withdrawals and transfers (`db::ledger::COMPONENTS_SQL`), cached 30 s in Redis (`ledger:projects`) and invalidated at admission, bump, every withdrawal notification and transfer. (5) Events follow their owner (below). (6) `internal_transfers` is append-only (trigger), idempotent (`idempotencyKey` = same staff + same parameters, else 422), one (network, token). (7) Nothing about custody reaches a project: no treasury/holdings/merchant-funds figure and no other project's figure in a merchant response or a project endpoint's payload — `/balances`, `/wallet-balances` and the Lightning history are staff-only (removed from the merchant router, 404).
- **Projects — before the first one exists** (spec §13): `jobs::projects::projects_exist` (static flag, 10 s negative cache) gates everything: legacy keys work unscoped (`CurrentApiKey.project_id = None` → `OwnerFilter::Any`), fan-out is not owner-filtered, the project check is off, and every route creating an owned object answers `409 "Create a project first"` (`require_any_project`). The first `POST /projects` runs under `pg_advisory_xact_lock(hashtext('projects-first'))`: `attach_existing` (default) moves legacy keys, addresses, key withdrawals and address-book entries to it and splits endpoints with `domain::split_legacy_endpoint` (a mixed one is duplicated into a merchant endpoint with the same URL/secret; `WITHDRAWAL_*` / `TRANSFER_COMPLETED` stay on both); `false` revokes the legacy keys (audit `api_key.revoked`, reason `no_project`) and makes the rest the merchant's.
- **Projects — ledger**: project balance per (project, network, token) = confirmed deposits + unattributed sweeps of its addresses (Bitcoin: `deposit_addresses.btcReceivedRaw`, raised only, from `chain.bitcoin_received_at_depth` = `funded_txo_sum` − fundings still short of `BTC_CONFIRMATIONS`, written by the sweeper's Bitcoin branch) − withdrawn − fees in the same asset (BTC, ETH) + transfers in − transfers out; `available` subtracts the project's open reservations. Native ETH sweeps store the **gross** balance (the sweep fee is a merchant cost); Lightning `amountRaw` is sats. Merchant funds = holdings (confirmed treasury balance from the `treasury-balance:{NETWORK}:{TOKEN}` cache + unswept addresses, `unknown` when the network is disabled, the provider fails or the pair's sweeps are off) − Σ project balances; a merchant-side transfer is bounded by them (`merchant_insufficient_funds`, `503 "Holdings unavailable, retry later"` on unknown). The treasury monitor (`monitor_once` → `ledger::check_shortfalls`, 5 min) counts consecutive shortfalls per pair in Redis (`ledger-shortfall:{NETWORK}:{TOKEN}`, reset on ok/unknown) and raises `LEDGER_SHORTFALL` (merchant endpoints, dedup 24 h) at 3.
- **API traffic log** (`api_requests`, Dashboard → Traffic): the `record_traffic` middleware must stay *outside* the auth guards in `router()` (added after both `nest`s, via `.layer` not `.route_layer`) so it sees rejected requests and the identity the guards copy into the **response** extensions (`CurrentApiKey` / `CurrentStaff`). It stores the matched route template, never the raw path or bodies, and **never the raw `x-api-key`** — only `apiKeyId`. The client IP honours forwarding headers only when the TCP peer is in `TRUSTED_PROXIES` (then the **last** `X-Forwarded-For` hop); otherwise it is the socket address. Recording is a non-blocking `try_send` into a bounded channel; drops are counted and exposed as `dropped_events`. `/api/v1` is the `MERCHANT` surface, `/api/admin/v1` is `ADMIN` (the dashboard's own polling — hidden by default in the UI); health checks are not recorded.
- **API key format**: `[{tag}_]{8 alnum}_{40 alnum}`. The tag is `app_settings.apiKeyPrefix` (≤ 5 alphanumeric chars, empty = no tag) and only affects newly generated keys. `auth::parse_api_key_prefix` is deliberately tag-agnostic (splits on the last `_`) so keys issued under any past tag — including the historic `spg` — keep validating after the setting changes. Never re-tighten it to a specific tag.
- **API key expiry**: `api_keys.expiresAt` (NULL = never) with status machine `ACTIVE`/`REVOKED`/`EXPIRED`. Enforcement is two-level: `find_api_key_by_prefix` rejects past-deadline keys immediately (the security boundary), while `api_key_expiry_loop` (5 min, first run at boot) only materializes `EXPIRED` for listings/stats. List handlers derive the displayed status so a key can never show `active` after its deadline, even between sweeps.
- **Confirmation thresholds**: Tron 19, Ethereum 12, Bitcoin 3 (env-overridable with floors, see Config), Solana hardcoded to 1 (`finalized` commitment, failed transactions skipped), Lightning 1 (a settled payment is final) — `domain::required_confirmations`. Tron reads only solidified history (`only_confirmed=true`) and resolves each transfer's real block through `walletsolidity/gettransactioninfobyid` (TronGrid's trc20 listing has no block number; never invent one). Provider responses are re-checked for the USDT contract. Zero-amount transfers never settle anything; `expected_amount` must be > 0.
- **Lightning rows**: `deposit_addresses.address` holds the BOLT11 payment request (matched by exact string) and `deposits.txHash` holds the SDK `Payment.id` — no dedicated payment-hash column. Two detection paths (SDK `PaymentSucceeded` events + a reconciliation poll from the oldest pending invoice) both converge on `process_detected_transfer`, made idempotent by the (address, txHash) upsert. The Lightning monitor loop reconciles every PENDING invoice (deadline passed or not) before its expiry sweep, so invoices paid during downtime are credited, not expired. SDK error strings are logged, never returned to clients (the deprecated payout alias answers a generic `502 "Payment failed"`; a withdrawal records a short failure code). `GET /lightning/payments` (keys allowed BTC on Lightning + ADMIN staff) pages the *whole* wallet history (`has_more`, no total), linking entries to gateway invoices via `deposit_address_id`. Merchant webhooks stay on the gateway's own queue — SDK events only feed detection (received payments) and payout notification (finished sends). Lightning withdrawals accept `user@domain` (no IP literals / local TLDs, and outside development the domain must resolve to public addresses: the SDK fetches it) or a BOLT11 invoice for exactly the amount — never one of the gateway's own invoices. The withdrawal id is the SDK idempotency key, so a retried send is answered from the SDK's storage; a withdrawal moves to BROADCAST *before* the SDK call (no cancel or re-check failure while a payment may be in flight), and one the wallet has no payment for after 3 min is handed to the SDK again (same key, advisory lock across containers). The deprecated payout alias answers a pre-upgrade `payout_requests` key from the wallet (its SDK id was the key) — never a new send — and its withdrawals take the `Idempotency-Key` as their id (hence SDK key), like the former flow.
- **Webhook delivery**: max 5 attempts (`WEBHOOK_MAX_ATTEMPTS`), 1 s loop, up to `WEBHOOK_DELIVERY_CONCURRENCY` (16) concurrent deliveries, 10 s HTTP timeout, only the *last* response/error is stored (`err.without_url()` — never the endpoint URL). Members are *claimed* atomically (Lua) from the queue ZSET into `zset:webhook-inflight` (score = lease expiry, `WEBHOOK_CLAIM_LEASE_SECS`): a member is never delivered twice concurrently (overlapping containers included), and a worker dying mid-delivery leaves a lease that puts the member back in the queue (at-least-once). Releasing reschedules with "keep the earlier score" semantics. Undecodable members (anything containing `|` that does not decode) are dropped, never re-fanned. A delivery whose endpoint went inactive/unsubscribed or whose subject is gone closes its PENDING row as FAILED instead of leaving it pending. Delivery rows are unique per key (partial unique indexes; `get_or_create_*` use `ON CONFLICT DO NOTHING` + re-select). Payloads carry top-level `event_id` (= delivery id = `X-Webhook-Id`) and `occurred_at`.
- **Webhook client** (`jobs::webhook_client`, `AppState.webhooks`): outside development `https://` only, no credentials in the URL, no internal names or non-public IP literals, a DNS resolver that only returns public addresses (`domain::is_public_ip`), and **no redirects** (3xx = failed attempt). In development `http://` and private receivers are allowed. Endpoint creation runs the same checks plus a DNS resolution.
- **Webhook signing**: `webhook_endpoints.secret` is stored in clear (HMAC needs it) but is **write-only through the API** — responses only carry `has_secret`; never serialize `WebhookEndpointRow.secret` into a handler response (its `Debug` is redacted). A secret is required at creation and cannot be removed (legacy unsigned endpoints keep delivering unsigned until one is set). Every delivery carries `X-Webhook-Id`, `X-Webhook-Timestamp`, `X-Webhook-Signature` (`sha256=<hex>` of the body, `auth::webhook_signature`) and `X-Webhook-Signature-V2` (`t=<ts>,v1=<hex>` of `"<ts>.<body>"`, `auth::webhook_signature_v2`), all computed over the exact body bytes sent — the payload is serialized once with `serde_json::to_vec` and that same buffer is signed and sent; never re-serialize separately.
- **Withdrawals — invariants** (spec §4, never relax them): (1) **persist before broadcast** — every outbound transaction is fully signed and stored in `outbound_transactions` (`SIGNED`) before it is broadcast; a restart re-broadcasts the same bytes, and a different transaction for the same purpose is only signed once the previous one is provably dead (Tron TAPOS expired *and* unknown to the node, Solana past `lastValidBlockHeight` *and* absent, ETH/BTC replaced with higher fees on the same nonce/inputs). (2) Sweeps and top-ups only go to the treasury address **computed from the seed** (`wallet.treasury_address`), never one read from the DB, settings or a request. (3) The freeze is checked right before signing **and** right before broadcasting (`outbound::may_broadcast_while_frozen`: only an already `BROADCAST` transaction is re-sent while frozen); the Bitcoin planning pass keeps running while frozen (`sweeper::planning_allowed`) because it only scans received amounts for the ledger and never signs. (4) `Idempotency-Key` + caller + parameters hash identify a withdrawal: a replay is answered from storage before any provider call; other parameters → 422. (5) Admission (`QUEUED` / `PENDING_APPROVAL`) happens only inside the per-asset advisory-lock transaction that checks every limit and the available balance (confirmed treasury − reservations − gas floor). (6) The worker re-checks approval, destination rules and the requesting key from the DB right before signing (`recheck_before_signing`); a raw destination that matched an address-book entry at creation keeps the entry as information only — once the entry is gone, `check_destination_rule` decides on the destination alone (an `OPEN` key or an admin below the threshold still sends, a `BOOK` key or an approval-level withdrawal fails `destination_not_allowed`). (7) Destinations never point at the gateway (deposit addresses and invoices, treasuries, their Solana token accounts — `resolve::is_gateway_destination`). Solana USDT: the token account is resolved once at admission and stored (`withdrawals.solanaTokenAccount`); a wallet destination must be empty or a System-program account and on the ed25519 curve; signing never re-reads a closed token account as a wallet. (8) Amounts are integer base units. (9) A sweep never changes a deposit's or a deposit address's status.
- **Withdrawal rules**: a key with `withdrawalPolicy = NONE` has no withdrawal surface at all — `GET /withdrawals`, `GET /withdrawals/{id}` and cancel answer 403 like create (`require_withdrawal_access`); a quote never carries the treasury's `available` / `fee_available` for a key (`rules::custody_figures_visible`, projects invariant 7); the admin `POST /lightning/payments` alias is gated by `require_any_project` like `POST /withdrawals`. Every admin transition (approve, reject, cancel, bump) takes its target status from `next_withdrawal_status` (`admin_transition`). A key withdraws only tokens/networks its grant allows (`withdrawalTokens`, `withdrawalNetworks` NULL = all), as its project (`Requester::ApiKey.project_id`, capped by the project balance — invariant 3 above); an admin names the owner (`project_id` UUID or `merchant`, required, `WithdrawalInput.owner`) and is not capped; `BOOK` keys only to active address-book entries **of their project** (24 h cooling-off, `activeAt`; `resolve_destination` scopes the book by owner), `OPEN` keys anywhere within their own per-token limits (required). Gas tokens are admin-only. At/above the asset's approval threshold any withdrawal waits in `PENDING_APPROVAL` (72 h, then cancelled), and an admin's must target an address-book entry (below it, admins send anywhere); approval needs another admin (a single active admin may self-approve after 24 h). Operators never withdraw; any staff may freeze, only an admin with TOTP unfreezes (never while `OUTFLOWS_FROZEN=true`). A key with a policy other than `NONE` must expire (DB CHECK) and granting it needs TOTP. Legacy `canSend` keys were migrated to `OPEN` for BTC on Lightning with the former payout limits; the old `payout_requests` rows still count in the BTC rolling-24 h usage.
- **Hot-wallet cap** (`asset_settings.hotWalletCapRaw`) is per asset: the monitor and `treasury_view` (`apply_cap_per_asset`) sum the asset's confirmed treasuries over every network, `cap_exceeded` is set on every row of the asset and `asset_holdings_raw` carries the sum the dashboard's "send excess" works from.
- **Outbound engine** (`jobs::outbound`): workers claim with `FOR UPDATE SKIP LOCKED` and hold a per-sender advisory lock (`db::outbound::lock_sender`) while allocating nonces (`signer_nonces`, resynced from the chain) or reserving UTXOs and signing — safe across two containers during a Kamal overlap. `decide()` (pure) maps an `Observation` to the next step. A broadcast error never proves a transaction dead (an earlier send whose answer was lost may have been accepted): only tracking closes one — ETH: its nonce used `ETH_NONCE_USED_DEPTH` (12) blocks deep, read *before* the receipt; Solana: block height (read *before* the signature status) past `lastValidBlockHeight` + 64 and no trace of it; Tron: TAPOS expiration passed and unknown to the node; BTC: an input spent by another transaction; a Bitcoin transaction Esplora no longer knows is re-sent as stored and counts its wait from `sentAtHeight` like one in the mempool (`stuck_since_sent`), so it escalates to RBF / STUCK instead of being re-sent at the same fee forever; a Solana failure is final at `finalized` only, like a success. A withdrawal with a landed (CONFIRMED / reverted FAILED) transaction is never signed again — `withdrawals_without_live_tx` skips it and `resign_dead` re-checks under the row lock (`has_open_or_landed_tx`); a run that died between the transaction's and the withdrawal's update is settled from the stored outcome (`settle_landed`). Before re-signing or abandoning, every transaction ever signed for the withdrawal (REPLACED / EXPIRED included) is looked up on chain and one found mined — or, on Bitcoin, back in the mempool — is tracked again instead (`revive_family`); siblings of a landed transaction are only marked REPLACED once it is final (a reorg may still mine one of them). A BROADCAST ETH transaction the node no longer knows is re-sent as stored. A withdrawal or sweep found waiting is skipped for the rest of the tick and goes to the back of the queue (`updatedAt`), never using up the per-tick budget. ETH/BTC replacements bump fees by 25 % up to the withdrawal's `feeCapRaw` (3 × the quote); past it the withdrawal goes `STUCK` (alert) until an admin bumps (doubles the cap) or abandons (only when provably dead); a Tron transaction the node still knows 10 min past its expiration goes STUCK at once (never replaced unproven). An RBF replacement refused for its fee is not dead: the next one escalates from its fees after the same wait (inputs and nonce stay the live transaction's — a closed attempt's extra inputs were released), and a closed replacement hands its inputs back to the live original before its reservations are released. Tron transactions are built by TronGrid but decoded and verified (owner, contract, recipient, amount, fee limit, expiration) before signing — never sign a node-built transaction unverified. Confirmation thresholds are the deposit ones.
- **Sweeps** (`jobs::sweeper`): per (network, token) above `sweep_settings.minimumRaw`; USDT on Ethereum/Tron first gets an exact gas top-up from the treasury (`GAS_TOPUP` purpose), Solana sweeps are paid by the treasury (fee payer) and close the emptied token account. Bitcoin is never swept. At most one open sweep per address, whatever its token (partial unique index on `depositAddressId`). Ethereum gas top-ups share the treasury's nonce sequence: a stuck one is fee-bumped (same nonce, up to 3 × its first fee per gas); sweeps themselves are not (logged only). Every Solana sweep idempotently creates the treasury's USDT token account (the first one pays its rent).
- Two independent status machines: deposit (`DETECTED` → `CONFIRMED`) tracks on-chain state; webhook (`PENDING`/`DELIVERED`/`FAILED`) tracks HTTP notification state. Never let one mutate the other.
- A deposit is unique per `("depositAddressId", "txHash")` (one Bitcoin tx can pay several gateway addresses) — look deposits up by both; derivation indices are allocated atomically per network from `derivation_counters` (`next_derivation_index`, Lightning too, though no key depends on it); `(network, derivationIndex)` is unique.
- **Merchant API bounds**: every `/api/v1` list and lookup is scoped to the key's project (`merchant_scope` → `OwnerFilter`); `GET /project` is the key's project + balances (409 `"This API key belongs to no project"` for a legacy key); `/transfers` is read-only; `/balances`, `/wallet-balances` and `GET /lightning/payments` are **not mounted** on `/api/v1` (404, the last one explicitly after the key guard); ETH `expected_amount` ≤ 100 000 with ≤ 18 decimals; `expires_at` within [now + 1 min, now + 1440 min]; at most `MAX_PENDING_ADDRESSES_PER_API_KEY` open payments per key (`deposit_addresses.apiKeyId`); a disabled network answers 503; `/balances` is served from a 5-minute Redis cache recomputed in the background (503 + `Retry-After` while computing); merchant webhook replays re-queue FAILED deliveries only; merchant responses never include endpoint URLs or delivery errors. Rate limits live in `http-api/src/rate_limit.rs` (Redis fixed windows keyed by the hashed identity).
- **Client IP** (`traffic::resolve_client_ip`, used by the traffic log, rate limits and audit): forwarding headers count only when the TCP peer is in `TRUSTED_PROXIES`; `X-Forwarded-For` is then walked from the right and the first untrusted hop is the client.
- Polling loops sleep `ADDRESS_REQUEST_DELAY_MS` (300ms) between addresses to respect provider rate limits; TronGrid additionally has an explicit backoff on 429s in `chain`.

## Security rules

This is a **custodial hot-wallet** service — treat everything key-related as sensitive:

- Never commit `.env`, real mnemonics, API keys, or production credentials. `.env.example` only uses the well-known BIP39 test vector (`abandon … about`) — refused outside development (`config::is_public_test_mnemonic`), and Lightning never connects with it.
- `AppConfig`, `WebhookEndpointRow` and `StaffUserRow` have hand-written, redacting `Debug` impls, and `AppConfig` zeroizes its secrets on drop: keep it that way when adding a secret field.
- Address derivation must remain deterministic — changing paths or hashing breaks recovery of funds on already-issued addresses. The same holds for the treasury paths (`packages/rust/wallet/src/lib.rs` golden tests). Keys never leave `wallet`: signing goes through the `Signer` trait (`KeyRef`), never an exported private key.
- The Breez SDK is seeded with the same `WALLET_MNEMONIC` (Spark paths do not collide with BIP44/84). Lightning funds sit in the Spark L2 wallet, a different custody model (README → Custody note); its storage (`BREEZ_STORAGE_DIR`, absolute) must persist, and `gateway` disconnects the SDK on SIGINT/SIGTERM.

## Git / CI / releases

- CI (`.github/workflows/ci.yml`) is **manual only** (`workflow_dispatch`, from the Actions tab on any branch; nothing runs on push or PR, so run it yourself before merging): `pnpm nx affected -t lint test build` (Rust toolchain + `protoc` from the shared `setup-rust` action; cargo runs `--locked`, clippy `-D warnings` — refresh `Cargo.lock` after editing a `Cargo.toml`), `cargo deny check` (`deny.toml`; a new ignore needs a reason), then a build of the `all` Docker image. Third-party actions are pinned by full commit SHA and base images by digest (the Dockerfile hard-codes Node 24.21.0: keep it in sync with `.tool-versions`); Dependabot proposes updates.
- Docker: one multi-stage `docker/Dockerfile` (targets `api`, `dashboard`, `all`); the dashboard's nginx config lives in `docker/dashboard/` (non-root, port 8080, `/up` health check, `/api` proxied to `API_URL`). `compose.yaml` runs the whole stack from images, `compose.dev.yaml` only postgres + redis (same project name and volumes).
- Deploys: **Kamal** (`config/deploy.yml`, one file for test/staging/production; `.kamal/secrets` holds env-var references only). Deploy runs only from `main` / `v*` for a commit on `main` (a `guard` job; a commit without a green CI run only gets a warning), loads the deploy key into an agent with `webfactory/ssh-agent` (the server's host key is accepted on first contact, not pinned), and both roles run with `no-new-privileges` + `cap-drop ALL` (dashboard read-only). nginx (`docker/dashboard/`) verifies the API certificate and adds the security headers of `security-headers.conf` — any location that adds a header must include it again. One image (target `all`) runs as two roles — `api` (proxy `API_HOST`, port 3000, health `/readyz`, Breez volume via role `options.volume`) and `dashboard` (`/app/dashboard/start.sh`, proxy `DASHBOARD_HOST`, port 8080). Postgres and Redis are **Kamal accessories** on the same server (one server per environment — every container/volume name is shared by all environments): images pinned by digest in `config/deploy.yml` (bumped by hand, Dependabot does not read it), named volumes (never bind-mounted `directories`: `kamal accessory remove` deletes those), no published port, non-root with every capability dropped, reached in plain text over the `kamal` docker network (hence `ALLOW_INSECURE_TRANSPORT=true` on the api role); `.kamal/secrets` builds `DATABASE_URL` / `REDIS_URL` from the `POSTGRES_PASSWORD` / `REDIS_PASSWORD` secrets (URL-safe, checked by the workflow). No automated backup (README → Database). `.github/workflows/deploy.yml` (manual, per GitHub environment) runs `kamal accessory boot all` (creates missing ones only; its `reboot-accessory` input recreates one to apply a change) then `kamal deploy`; hosts come only from GitHub variables (`GATEWAY_HOST`, `API_HOST`, `DASHBOARD_HOST`). A deploy overlaps the old and new api containers for a few seconds on the Breez volume (accepted: idempotent processing). Never put a secret value in `config/deploy.yml` or `.kamal/secrets`.
- Releases are **manual** via the "New App Version" workflow (`workflow_dispatch`): it bumps the workspace version with `cargo set-version`, commits `chore: release vX.Y.Z`, tags, and publishes the Docker image. Never bump the version or create tags by hand.
- Do not commit or push unless the user asks. Keep PRs scoped to one concern; add tests when changing `domain` or `wallet` logic.
